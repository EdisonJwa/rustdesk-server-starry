# 客户端策略下发 —— 安全边界

状态：**约束性文档**（2026-11-28）
适用：`/api/heartbeat` 及所有写入 `client_strategies` 的代码

[English](CLIENT-STRATEGY-SECURITY.md) | 简体中文

## 这是什么

客户端每三秒轮询 `POST /api/heartbeat`。当响应携带 `strategy.config_options` 时，客户端
把这些键直接喂给自身的 `Config::set_options`。这是**服务端发起的客户端配置变更**，
也是协议里唯一这样的通道。

本功能的开发计划写明：安全边界必须先于代码。本文就是那个边界。下面的实现逐条照此执行；
本文不允许的，一律不实现。

## 威胁模型

| 攻击者 | 能力 | 若不设防的后果 |
| --- | --- | --- |
| 任何能访问 API 的人 | `POST /api/heartbeat` | 无认证时可冒充任意设备，领取本属于他人的策略 |
| 被攻破的账号持有者 | 读取自己的策略 | 可接受——策略是配置，不是机密 |
| 被攻破的服务端数据库 | 写 `client_strategies` | 攻击者控制全网客户端配置；白名单是限制损害范围的关键 |
| 网络攻击者 | 篡改响应 | TLS 止于 Caddy；客户端不做校验，完整性完全依赖传输层 |

## 四条规则

### 1. 只有已认证设备能收到策略

心跳请求标识一台设备，只有其所有者能收到该设备的策略。未认证的心跳**仍然应答**——
协议要求给出响应，否则客户端会重试——但响应中**没有** `strategy`，也没有 `sysinfo`
指令，只有 `modified_at`。

若部署完全没有配置认证，则策略下发整体关闭，而不是退化为匿名下发。一台不知道
"提问者是谁"的服务器，无法安全地回答"你应该怎么配置"。

### 2. `config_options` 走白名单，白名单是"不可能削弱安全性的键"的并集

允许的键及理由：

| 键 | 为何安全 |
| --- | --- |
| `relay-server` | 把媒体改经运维指定的中继。无法放开访问权 |
| `rendezvous-server` | 同上，作用于信令。错值会断连，不会放大权限 |
| `api-server` | 把客户端指向本服务器，本已被信任 |
| `allow-auto-record-incoming` | 录制策略。涉及隐私，但范围限于用户自己的机器 |
| `enable-audio` | 功能开关 |
| `enable-clipboard` | 功能开关 |
| `enable-file-transfer` | 功能开关 |
| `enable-remote-printer` | 功能开关 |
| `use-webrtc` | 传输选择 |
| `allow-remote-config-modification` | 是否允许本通道生效。下发 `N` 是关闭它，严格收窄 |
| `verification-method` | 提供哪些第二因素 |

**不在表内的键一律丢弃，并以 `warn` 级别记录键名。** 这份清单在构造上就是穷尽的：
`strategy::ALLOWED_KEYS` 是唯一来源，且有测试断言"含未列键的文档只下发已列键，其余全无"。

明确禁止项及理由：

| 键族 | 为何永不 |
| --- | --- |
| `password`、`key`、`secret`、`token`、`private-key` | 凭据。远程写入即凭据注入 |
| `whitelist`，以及录制/配置开关之外的 `allow-*` | 放开权限。任何授予能力的 `allow-` 键默认排除；上表三项是"功能开关"，本就需用户自己同意 |
| `deny-*` / 黑名单 | 移除运维设定的黑名单属放开操作 |
| 带 `is-public` 语义的 `custom-rendezvous-server` | 可把客户端迁往攻击者控制的中继 |
| `stop-service` | 关停客户端。属可用性而非安全，但远程杀开关不在范围内 |

### 3. 策略绑定账号，按 `modified_at` 下发

`client_strategies` 以 `user_id` 为键。设备收到的是"认证该心跳的那个账号"的策略。
不存在"全局策略"下发给所有设备，否则任何一次认证都等价于任何其他认证。

`modified_at` 收窄是正确性要求而非优化：客户端记住上次见到的值并回传；重复下发未变化的
文档会让客户端在每次轮询时重新应用配置。

### 4. `disconnect` 与 `strategy` 分离，且不携带配置

`disconnect` 是要断开的连接 id 列表。它不改变任何配置，也无法用于放大权限，因此不需要
白名单——但同样需要认证，因为强制关闭他人会话是一个拒绝服务原语。

## 本通道不是什么

- **不是授权通道。** 它不决定连接是否允许；那是 hbbs 上 `STARRTY_STRATEGY_FILE` 的职责。
  此处下发的任何内容都无法让 hbbs 接受它本会拒绝的连接。
- **不是凭据通道。** 此处的任何键都不得携带机密。
- **不持久。** 从不轮询的客户端只是保持上次配置；下发是拉取模型，因此灰度期间离线的设备
  会在回来时取到变更。

## 门禁

- `strategy::filter_config_options` 单测：每个已列键通过，每个禁止键被丢弃，未知键被丢弃，
  且函数是纯的。
- 测试断言 `ALLOWED_KEYS` 与 `FORBIDDEN_KEYS` 互斥——同时出现在两者中会让结果依赖遍历
  顺序。
- e2e：已认证心跳收到自己的策略；未认证的只收到 `modified_at`，无 `strategy`。
- 变异：让过滤器全部放行，则断言"禁止键不出现"的 e2e 必须失败。
