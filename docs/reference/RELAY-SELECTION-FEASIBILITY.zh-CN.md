# 我们能不能做中继择优 —— 能力边界研究

状态：研究完成（2026-11-28）
结论：**对官方客户端能做"分流"和"排除"，不能做"测量择优"。** 原因在协议，不在实现。

[English](RELAY-SELECTION-FEASIBILITY.md) | 简体中文

## 一、问题拆成两半

"择优"可以指两件不同的事，能做的程度完全不同：

| 含义 | 需要什么 | 我们能不能 |
| --- | --- | --- |
| **A. 分流**：把不同客户端分到不同节点，避免一台闲置 | 客户端 IP、GEO 规则、轮转 | **能，且已经能做** |
| **B. 测量择优**：同一客户端比较多个节点，选当前最快的那台 | 客户端对多个候选测速并回报 | **对官方客户端不能** |

本研究的重点是 B，因为 A 只是配置工作。

## 二、为什么 B 对官方客户端做不到

### 2.1 协议只允许一个地址

`libs/hbb_common/protos/rendezvous.proto` 里所有 `relay_server` 字段都是单值 `string`，
**没有任何候选列表字段**：

```
PunchHoleResponse.relay_server = 4   string
RelayResponse.relay_server    = 4   string
```

客户端 `src/client.rs:1028`：

```rust
relay_server = ph.relay_server;   // 一个地址，直接用
```

`src/client.rs:1359` 把它交给建连，**没有"多个取最优"的分支**。服务端下发什么，
客户端连什么。

### 2.2 官方客户端不测中继质量

这是决定性的。它有两个探测，但都不是针对中继的：

| 探测 | 测什么 | 何时 | 结果去向 |
| --- | --- | --- | --- |
| `TestNatRequest` | **NAT 映射端口**，不是延迟 | 连接之前 | 只用来定 UDP 打洞端口 |
| `TestDelay` | **端到端回环延迟**（含服务端事件队列） | 连接之后，在已建会话上 | 仅显示给用户，不参与选路 |

`src/client.rs:5478` 的注释甚至明确说明 `TestNatRequest` 只用于端口发现：

```rust
// The punch port must come only from the rendezvous server's TestNatResponse, which
// observes THIS socket's public mapping.
```

**所以客户端手上没有任何"这台中继此刻多快"的信息**，不可能自行选择。

### 2.3 我们已有的 `relay_quality` 正是 B，但需要客户端配合

`src/relay_quality.rs`（约 1000 行）已经实现了完整方案：服务端给候选集 → 客户端逐台
测速回报 → 服务端按 RTT/抖动/丢包排序锁定。

**它要求 `client_protocol == 1`，而官方客户端全仓没有任何 `relay_quality` 引用。**
这是 Starry 私有协议。

## 三、那"能做"的边界在哪

### 3.1 能做：按客户端属性分流（今天就能）

因为"规则按顺序匹配、取第一个命中"，同国多节点可以拆成多条规则：

```yaml
geo:
  rules:
    - name: CN 广东 → 广州
      match: { client_a: CN, client_a_isp: "China Telecom Guangdong" }
      relays: [117.78.7.96:21117]
    - name: CN 其余 → 上海
      match: { client_a: CN }
      relays: [cn-2:21117, 117.78.7.96:21117]
```

可按国家、省份、ISP、ASN 分。**这是真实的分流，且对官方客户端生效。**

局限：同一 ISP 内的客户端仍全落一台；需要 MMDB 真能区分 ISP。

### 3.2 能做：稳定轮转，把"主备"变成"分担"

默认同一规则内仍取 `first()`，第二台只在第一台 TCP 不可达时才用。设
`STARRY_RELAY_SPREAD=1` 后改为按客户端稳定哈希取模：

```rust
let index = stable_hash(&client_addr) % candidates.len();
```

- 收益：一国多节点平时就分摊，而不是一台干活一台闲置。
- 约 50 行 + 测试。
- 同一客户端稳定落同一台，不影响连接复用。
- **已实现，默认关闭**（`src/rendezvous_server.rs` 的 `pick_within`）。默认关的原因：
  第二台常是另一个站点、有自己的带宽成本；且共享 NAT 出口的客户端会被哈希压到同一台。
  开关的取舍见 [MULTI-NODE-SELECTION.zh-CN.md](MULTI-NODE-SELECTION.zh-CN.md) 第七节。

### 3.3 能做：服务端排除劣化节点（有前提）

hbbs 可以对自己的 `relay_servers` 做质量探测，但**只能用来排除，不能用来排序**：

**根本局限**：hbbs 在香港测广州节点和上海节点，测出的是 **hbbs 的位置差异**，不是
大陆用户的差异。用它排序会系统性地偏向离 hbbs 近的节点，与用户体感无关。

所以可行的形态是阈值判定：

```
某中继丢包 > 20% 或 RTT > 3× 组内中位数  →  标记为降级，排除出候选
其余保持配置顺序
```

这能救掉"某节点半死"的场景，且不会被 hbbs 视角带偏。

### 3.4 不能做：精细的按延迟排序

同上，缺客户端侧数据。任何基于 hbbs 视角的精细排序都是**伪择优**——看起来在挑最好的，
其实在挑离 hbbs 最近的。

## 四、一个容易被忽略的选项：客户端配置生成器

我们已有 `starry-client-config`，它生成导入串。**可以按用户生成不同的导入串**：

```json
{"host":"rustdesk.edison.network","relay":"117.78.7.96:21117","api":"...","key":"..."}
```

如果运维知道某批用户在某地区，可以给他们**指定 relay 的导入串**。这不是自动择优，
但是**确定性的分流**，且完全不依赖协议扩展。

- 收益：分批灰度、把大客户钉到专属节点、故障时定向迁移。
- 代价：0（工具已存在）。
- 局限：需要人工分批；用户换设备要重发导入串。

## 五、结论与建议

| 能力 | 官方客户端 | 需要什么 |
| --- | --- | --- |
| 按地区/ISP 分流 | ✅ | 配置 |
| 按用户分批指定中继 | ✅ | 导入串 |
| 同组内稳定分担 | ✅ | 约 50 行代码 |
| 排除劣化节点 | ✅ | 服务端探测 + 阈值 |
| 按实测延迟优选 | ❌ | 私有客户端协议 |
| 多候选下发 | ❌ | 改协议，且客户端不认 |

**建议顺序**：

1. **稳定轮转**（3.2）——最小改动，把闲置的第二台用起来。**已完成，默认关**（`STARRY_RELAY_SPREAD=1`）。
2. **规则分流**（3.1）——纯配置，立即可用。
3. **阈值排除**（3.3）——防"半死"节点，避开 hbbs 视角的陷阱。
4. 不做 3.4 的精细排序，除非我们同时维护客户端分支。

**一句话**：对官方客户端，我们能把"主备"做成"分担"，也能把"坏的"剔掉，但做不到
"逐次挑最快的"。这不是工程量问题，是协议里没有那个字段。

## 六、如果将来要真做择优

唯一路径是**同时维护客户端**。届时现有 `relay_quality` 可以直接用——它已经写好并测试过
（协议版本 1，`max_candidates` 1–5，含滞留机制防抖动）。所以现在不做，不等于白写：
它是那条路的前置件，且默认关闭不影响任何人。
